# 批发经营台账 V1 Spec

Status: ready-for-agent

## Problem Statement

我需要制作一个面向中国大陆小型五金耗材批发商的个人作品集项目，用真实可操作的软件证明自己能够理解业务、设计领域规则，并独立完成 TypeScript 全栈开发、测试、本地交付和演示材料，而不只是拼装一组后台页面。

许多小型批发团队仍分别使用 Excel、聊天记录和纸质单据记录客户、销售、库存和欠款。这些记录之间缺少稳定联系，难以清楚展示一笔销售单确认后如何预占库存、出库后如何形成应收、客户部分付款后还剩多少未收金额。原项目方案同时纳入采购、应付、退货、盘点、扫码和部署，范围不足以形成明确终点，也混淆了销售单履约状态与应收结算状态。

本项目不能访问真实从业者或真实经营数据，也不准备承担线上部署成本。因此它必须被诚实地定位为使用虚构数据、未经真实客户验证、仅在本地运行的演示项目；其价值来自边界清楚、规则可信、数据可追溯、环境可复现和展示材料完整。

## Solution

制作“批发经营台账 / Wholesale Ops”首版：一个公开源码、可在本地完整运行的中文经营后台。首版只完成销售闭环，将销售单履约、库存和经营应收连接起来：销售创建销售单，确认时校验并预占库存，仓库完整出库，系统生成一笔经营应收，财务登记一次或多次收款，老板通过经营总览查看销售、收款、逾期和库存预警。

系统提供老板、销售、仓库、财务四种固定角色和服务端数据边界；提供 SKU、客户、期初库存的 `.xlsx` 导入，以及销售单、应收和库存流水导出；所有关键动作留下业务审计记录。演示环境包含可重复重置的虚构数据、确定的演示账号和固定业务场景。

首版以本地可复现和作品集证据为交付目标，不上线、不开放注册、不实现完整进销存或财税能力。采购、应付、退货、盘点和扫码作为独立后续路线图，不阻塞首版完成。

## User Stories

1. 作为项目作者，我想用一个边界清楚的销售闭环展示作品，以便证明自己能完成业务分析和全栈交付。
2. 作为项目作者，我想明确声明数据均为虚构数据，以便不让观看者误以为项目已经过真实客户验证。
3. 作为项目作者，我想明确声明系统不是财税系统，以便避免把经营应收误解为会计凭证或税务数据。
4. 作为技术评审者，我想从公开仓库复现项目，以便验证项目不是只能在作者电脑上运行的演示壳。
5. 作为技术评审者，我想通过一套简短命令完成数据库启动、迁移和种子数据初始化，以便快速审查项目。
6. 作为项目作者，我想一键重置虚构演示数据，以便重复录制相同的演示流程。
7. 作为项目作者，我想备份和恢复本地数据库，以便展示基本的交付与恢复能力。
8. 作为未登录访客，我想被引导到登录页面，以便理解系统需要身份认证。
9. 作为系统用户，我想使用预置账号和密码登录，以便进入与我角色相符的工作区。
10. 作为系统用户，我想退出当前会话，以便结束访问。
11. 作为老板，我想创建、停用账号并分配固定角色，以便控制团队成员的访问权限。
12. 作为老板，我想为一个账号分配多个角色，以便适应小团队一人兼任多项工作的情况。
13. 作为老板，我想查看全部经营数据和业务审计记录，以便掌握完整经营情况。
14. 作为销售，我想只能查看和维护由自己负责的客户，以便遵守客户数据边界。
15. 作为销售，我想只能查看自己负责客户的销售单和收款进度，以便跟进自己的销售关系。
16. 作为仓库，我想只看到出库所需的客户名称、联系人、电话和地址，以便履约而不接触价格与应收。
17. 作为财务，我想查看全部客户和应收，以便登记收款和核对未收金额。
18. 作为财务，我想不能修改客户、SKU 或库存流水，以便职责边界清楚。

## Implementation Decisions

- 产品名称使用“批发经营台账”，英文副标题使用“Wholesale Ops”；不使用“ERP”或“财税系统”作为产品定位。
- 业务语境固定为中国大陆五金耗材批发，界面使用简体中文、人民币和中国标准时间。数据全部虚构，未经真实客户验证。
- 首版只实现销售单—库存—经营应收闭环。销售单履约状态与应收结算状态分别维护，不存在同时代表履约和回款的笼统“完成”状态。
- 销售单状态固定为草稿、已确认、已出库、已取消。草稿可编辑或删除；确认后业务内容冻结；已确认销售单只能在出库前填写原因取消；已出库和已取消销售单永久保留。
- 销售和老板可以确认销售单；销售只能操作自己负责客户的销售单，老板可以操作全部销售单。仓库完成出库，财务和老板登记或撤销收款。
- 首版只有一个仓库，不提供仓库选择、调拨或跨仓查询。
- 每个 SKU 使用唯一且不可变的 SKU 编码和一个固定库存单位。不同包装规格是不同 SKU；数量为正整数，不支持按米、公斤等拆零计量。
- 现存量表示仓库实际持有数量，预占量表示已确认但尚未出库的承诺数量，可用量等于现存量减预占量。库存预警以可用量小于或等于预警值判断。
- 确认销售单时为所有明细一次性建立预占。任一 SKU 可用量不足则整个确认失败；不支持部分预占、欠货或分批出库。
- 库存预占必须防止并发超卖。确认、取消和出库均通过数据库事务原子地修改预占、库存流水与业务审计；库存竞争使用可重试的串行化事务。
- 首版采用现场交货或自提的简化经营场景，完成出库即视为交付。出库一次性交付销售单全部商品，同时减少对应现存量与预占量，并按成交金额生成一笔经营应收。
- 参考售价只用于草稿默认值；成交价可在草稿中调整，采用人民币含税口径并精确到分。确认后冻结价格。首版不计算税额、成本、毛利或利润。
- 客户使用唯一且不可变的客户编码，客户名称可以重复；每个客户只有一名当前客户负责人。客户默认账期支持现结或按天数表达，销售单保存交易时的客户和账期快照。
- 到期日按出库日加销售单账期快照计算。应收结算状态为待收款、部分收款、已结清；超过到期日仍有未收金额时派生为逾期应收。
- 一笔收款只指定一笔应收，一笔应收可以有多笔收款。收款金额必须大于零且不超过未收金额；不支持预收款、客户余额、跨单分摊或自动核销。
- 收款记录收款日期、金额、方式、参考号和备注。方式固定为现金、银行转账、微信、支付宝和其他。
- 已登记收款不能编辑或删除。财务或老板通过填写原因创建撤销收款反向记录，恢复未收金额并保留原收款。
- 固定角色为老板、销售、仓库和财务，一个账号可以拥有多个角色。首版不提供自定义角色或权限编辑器。
- 老板查看全部数据并管理账号、角色和基础资料；销售只访问自己负责的客户、销售单及其收款进度；仓库只访问库存、待出库任务和必要履约联系方式，不访问成交价或应收；财务访问全部客户和应收，但不能修改客户、SKU 或库存流水。
- 权限在服务端统一检查登录、角色和数据范围。客户端隐藏或禁用操作只用于改善体验，不能作为安全边界。
- 已被业务记录引用的 SKU 和客户只能停用，不能删除；唯一编码一经创建不可修改。
- 期初库存是库存流水的起点，只能在尚未发生销售库存活动时导入。首版没有直接修改现存量、补货、采购或盘点调整入口。
- `.xlsx` 导入分为 SKU、客户和期初库存三个固定模板。文件最大 10 MB、每次最多 2,000 行；不接受宏、不计算公式、不保存上传原文件。
- 导入流程为解析、逐行校验、展示预览、用户确认、单事务写入。任何一行错误都使整批不能写入；重复编码、缺失字段和非法数值必须定位到具体行。
- 使用 SheetJS Community Edition 的官方发行包在服务端解析和生成 `.xlsx`，不使用 npm registry 中过期的 `xlsx` 包。
- 销售单、应收和库存流水列表按当前权限与筛选条件直接导出 `.xlsx`。不保存导出文件或导出历史，但导出动作进入业务审计。
- 业务审计使用 PostgreSQL 中只追加、只读展示的记录，保存操作者、动作、对象类型与标识、时间、原因、关联编号及必要变更摘要。它不构成事件溯源、防篡改系统或合规认证。
- 运行日志使用 Pino 输出本地结构化日志。密码、授权头、Cookie、会话、原始导入行和客户敏感字段必须脱敏或排除；不接入 Sentry、云日志或外部可观测平台。
- 经营总览显示今日销售额、今日收款额、未收金额、逾期金额、库存预警和最近三十日收款趋势；所有时间计算使用 `Asia/Shanghai`。
- 应用采用 Node.js 24 LTS、pnpm 11、Next.js 16 App Router 单体架构。查询使用服务端组件，写入口只负责输入校验、鉴权和调用领域服务；业务规则集中在纯 TypeScript 领域/应用服务中。
- 本地数据库由 Docker Compose 运行 PostgreSQL 18，应用在宿主机运行。仓库提交依赖锁文件、Node 主版本约束和环境变量示例。
- 数据访问采用 Prisma ORM 7、Prisma Migrate 和 PostgreSQL 驱动适配器。提交数据模型和版本化 SQL migration，不用无迁移历史的 schema push 作为正式初始化方式。
- 认证采用 Better Auth 的邮箱密码登录与数据库会话，关闭公开注册、邮件验证、找回密码和第三方登录。种子数据创建老板、销售、仓库、财务四个单角色账号和一个多角色账号。
- UI 采用 Tailwind CSS 4、经过视觉定制的 shadcn/ui、TanStack Table 和 Zod。桌面是主要演示环境；390px 手机宽度只要求常用查询和基础操作不被布局阻断，不要求移动出库或扫码。
- 主验收浏览器为最新版 Chrome。首版不设正式 WCAG、键盘全覆盖或多浏览器兼容认证，但基础表单必须可理解、错误信息必须清楚。
- 本地工作流提供环境初始化、开发启动、演示数据重置、数据库备份和恢复命令。重置和恢复属于破坏性操作，必须显示明确警告；认证密钥在本地生成，不提交到公开仓库。
- 演示种子数据包含 30 个 SKU、8 个客户、5 个账号、20 张历史销售单、至少 2 张待出库销售单、2 笔部分收款、2 笔逾期应收和 5 个库存预警 SKU，并包含库存刚好足够与库存不足场景。
- 种子数据日期相对重置当天生成，使今日与逾期场景持续有效；账号、数量、金额和场景规则保持确定，连续重置三次结果一致。
- GitHub Actions 在提交和拉取请求时运行依赖安装、代码检查、类型检查、单元/集成测试和生产构建；关键浏览器旅程可使用独立工作流。
- 首版只有在销售闭环、权限、导入导出、审计、自动化测试、本地初始化与重置、备份恢复、README、License、截图、流程图和演示视频全部通过验收后才算完成。没有上线或获客指标。

## Testing Decisions

- 好测试只验证用户可观察的结果和稳定业务契约，不断言内部函数调用次数、组件树、ORM 调用顺序或私有实现细节。
- 仓库目前没有实现或测试先例。首版建立三层高位测试接缝，之后优先复用，不为每个模块创建独立测试入口。
- 第一层接缝是纯 TypeScript 领域/应用服务。Vitest 通过命令输入和结果/错误验证销售单状态跳转、金额计算、账期快照、到期日、角色权限和数据范围规则。
- 第二层接缝是应用服务加真实 PostgreSQL。Testcontainers 启动 PostgreSQL 18，执行真实 migration，验证唯一约束、事务回滚、库存流水、业务审计、并发预占、取消、出库、收款与撤销收款的原子结果。
- 第三层接缝是浏览器关键旅程。Playwright 使用真实应用和数据库，从登录开始验证四类角色权限、完整销售闭环、部分收款、撤销收款、Excel 错误预览、导出和演示数据重置。
- 领域测试必须覆盖草稿之外状态不可编辑、非法状态跳转、库存不足整单失败、同时确认最后库存只有一个成功、取消释放预占、重复出库失败和已出库不可取消。
- 金额测试必须覆盖人民币定点计算、零或负收款拒绝、超额收款拒绝、多次部分收款、结清状态、撤销后未收金额恢复和逾期判断。
- 权限测试必须覆盖每个角色的允许操作、拒绝操作和行级数据范围；必须直接调用服务端入口验证，不能只测试按钮是否隐藏。
- 导入测试必须覆盖正确模板、空文件、错误工作表、超过大小或行数、重复编码、数据库既有编码、缺失字段、非法整数、非法金额、公式和整批回滚。
- 导出测试验证权限和当前筛选条件影响导出内容，且导出动作产生业务审计；不依赖工作簿内部非契约性元数据。
- 日志测试只验证明确要求的敏感字段不会出现在输出中，不对完整日志文本做脆弱快照。
- 种子与重置测试连续运行三次，验证账号、数量、金额、预警、待出库、部分收款和逾期场景保持确定；相对日期符合重置当天的中国标准时间。
- 生产验收要求代码检查、类型检查、全部自动化测试和生产构建通过。首版不以全仓覆盖率百分比作为目标，而要求每条关键业务规则同时具备成功和失败用例。
- 主浏览器自动化只运行 Chromium。最新版 Chrome 进行人工演示验收；手机宽度进行布局冒烟检查，不建立正式多浏览器或无障碍认证套件。

## Further Notes

- 领域词汇以仓库根目录的领域词汇表为准。实现、测试、界面和后续工单应统一使用“销售单”“现存量”“预占量”“可用量”“应收”“收款”“撤销收款”等正式术语。
- “出库即交付并生成应收”是本演示针对现场交货或自提场景采用的产品规则，不是所有批发业务的行业通则。
- 经营应收只帮助演示销售、库存和欠款联动，不代表收入确认、会计处理、税务发票或法律上的债权证明。
- 首版接受“已出库后无法在系统内纠错”的明确限制。演示录入错误通过演示数据重置恢复；第二阶段应优先设计退货验收入库、应收调整和必要退款。
- 公开材料应明确写出项目是个人作品、所有数据虚构、未经真实客户验证、只支持本地运行、不是财税系统且没有在线演示。
- 项目完成由可验收成果定义，不设置时间盒；新增想法只有在不扩大首版完成定义时才能进入当前范围，否则记录到后续路线图。
